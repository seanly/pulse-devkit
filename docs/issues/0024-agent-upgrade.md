# 0024 agent.upgrade：换掉自己的二进制

**里程碑** M5 · **依赖** 0018, 0019, 0023, 0025

## 目标

1000 台不可能手工升级。但一个坏的自升级能一次废掉整个机群 —— 它改的正是控制通道本身。

所以这个 issue 的内容其实是**怎么失败**。成功路径只有十几行。

## 机制在 agent，策略在服务端

这是唯一需要两边配合的原语：

| agent（机制） | 服务端（策略） |
|---|---|
| 下载、校验、冒烟测试、切换 | 谁升、什么时候升 |
| 失败自动回滚 | 分几批、每批多大 |
| 上报新版本 | 健康门与熔断阈值 |

策略那半在 [0025](0025-fleet-rollout.md)（分批编排）。这个 issue 只做机制。

## 成功路径

```
1. 按 digest 拉二进制（走 blob，1000 台拉同一个包，按 digest 缓存）
2. 校验 checksum + 签名
3. 写到新路径，不覆盖当前的
4. 跑 `新二进制 --version`           ← 冒烟测试
5. 原子 rename + 重启
6. 写 pending 标记（落盘，不是内存）
7. 新进程成功心跳一次 → 清除标记
```

## 第 2 步：签名不是可选的

一个只校验 checksum 的自升级，在服务端被攻破时毫无保护 —— 攻击者控制服务端，当然也控制它声称的 checksum。

签名要用**和服务端凭据无关的密钥**。如果用同一把 master key，那么攻破服务端就等于拿到签名能力，签名就成了装饰。

公钥在 agent 的本地配置里，服务端推不了（issue 0023 的同一条原则）。这意味着轮换签名密钥需要碰每台机器的配置文件 —— 不方便，而这个不方便就是它的价值。

## 第 4 步：冒烟测试挡掉的那一类

`新二进制 --version` 能退出 0，说明它至少：能被当前内核执行（架构对）、动态链接能解析（如果不是静态的）、不会在 `init()` 里 panic。

挡不掉的：只在连接服务端时触发的崩溃、配置解析在特定配置下的 panic。那些留给第 6-7 步。

## 第 6-7 步：死人开关，以及它的缺口

启动时先看 pending 标记：存在且已超过期限还没清除过，说明上次升级后**没能连上服务端** —— 自动换回旧二进制。

这个机制不依赖服务端的任何配合，这是关键。它工作在服务端已经联系不上的那个场景里。

**诚实的缺口：如果新二进制一启动就崩，没人去读那个标记。**

第 4 步挡掉大部分这种情况，但不是全部。彻底解决要一个不自升级的最小 supervisor —— 那是又一个要维护、要分发、要自己保证正确的二进制，而它的失败模式更难排查。

所以：**接受这个缺口，写在文档里**，靠三件事兜住：

1. 冒烟测试（挡掉"根本起不来"）
2. **灰度**：第一批 1 台。失联则后面 999 台根本不会升
3. systemd 的 `Restart=on-failure` + 旧二进制保留 —— 人工恢复是一条 `mv` 命令，不是重装

第 2 条是最有效的。自动回滚覆盖「能起来但连不上」，灰度覆盖「起不来」。两者都不覆盖的情况（第一批那 1 台起不来）需要人工，但那是 1 台而不是 1000 台。

## 不做的事

**不做跨大版本的自动升级。** 协议可能变、配置格式可能变。`agent.upgrade` 的载荷里带目标版本，agent 拒绝跨越它不认识的边界 —— 宁可报错让人来看，不要自己猜。

**不做降级。** 回滚是「恢复上一个二进制」，不是「安装一个更老的版本」。前者 agent 自己有，后者是一次正常的升级流程。

## 验收标准

- [ ] 签名校验，用独立于 master key 的公钥，公钥来自本地配置
- [ ] 签名错误 / checksum 错误 → 拒绝，不切换，回报原因
- [ ] 冒烟测试失败 → 拒绝，不切换
- [ ] pending 标记落盘；agent 重启后仍然有效
- [ ] 死人开关：模拟「升级后连不上服务端」，确认自动恢复旧二进制，有测试
- [ ] 旧二进制保留，人工恢复路径写在文档里
- [ ] 跨大版本拒绝执行
- [ ] 文档写明「一启动就崩」这个缺口，以及灰度为什么是它的对策

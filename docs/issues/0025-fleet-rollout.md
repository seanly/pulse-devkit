# 0025 分批、健康门、熔断

**里程碑** M5 · **依赖** 0011, 0018

## 目标

永远不要同时在 1000 台上执行写操作。

## 为什么这在框架里

策略归应用 —— 分几批、阈值多少、等多久，那是 certpulse（或任何消费者）的决定。

但「派一批 → 等完成 → 检查健康 → 决定是否继续」这个**编排**对任何向机群下发变更的系统都一样。而且它是最容易写错的部分之一：写错的后果是一个坏变更全量铺开，也就是这套能力最糟的失败模式。

`pulsequeue` 已经按 agent 容量派发；这个 issue 加的是**跨 agent 的批次与闸门**。

## 形状

```go
// Rollout 把一批 job 分组派发，每组之间过一道闸门。
type RolloutOptions struct {
    // Batches 是每批的大小。[]int{1, 10, 100, 0} 表示 1 台 → 10 台 →
    // 100 台 → 剩下全部（0 = 剩余）。
    //
    // 第一批是 1 而不是 10，因为第一批的全部价值在于「这个变更在真实
    // 主机上到底行不行」，而 1 台就能回答，代价最小。
    Batches []int

    // Gate 在每批完成后被调用，决定是否继续。
    //
    // 应用实现它：certpulse 会在这里检查 agent 还在不在线、拨测还通不通。
    // 框架不知道「健康」是什么意思。
    Gate func(ctx context.Context, batch BatchResult) GateDecision

    // SettleFor 是每批完成后、调用 Gate 之前的等待。
    //
    // 不是礼貌性的延迟：有些失败要时间才显现。换掉 CA 信任库之后 agent
    // 还会用现有连接心跳一会儿，真正的失败在它下次重连时才暴露 —— 那是
    // 一个心跳周期之后的事。
    SettleFor time.Duration

    // MaxFailureRate 是框架自己的熔断：超过这个比例就停，不问 Gate。
    //
    // Gate 之外再加一层，因为 Gate 是应用代码，而应用代码会有 bug。一个
    // 永远返回「继续」的 Gate 不该让坏变更铺满机群。
    MaxFailureRate float64
}

type GateDecision int

const (
    GateContinue GateDecision = iota
    // GateHalt 停止派发后续批次，已完成的批次保持原样。
    //
    // 不自动回滚：框架不知道怎么撤销一个它不理解的变更。停在原地并说清
    // 「做了 11 台，剩下 989 台没做」，比猜一个撤销动作安全。
    GateHalt
)
```

## 停住，而不是回滚

熔断的动作是**停止派发**，不是撤销已完成的部分。

因为框架不知道怎么撤销一个它不理解的变更。`fs.put` 有备份可以恢复，`exec.run` 跑过的 Ansible playbook 可能做了十件事 —— 框架无从知道怎么往回走。

所以熔断后的状态是「11 台已变更，989 台未变更，停在这里」，并把这件事说清楚。撤销是运维看完之后的决定，可能是另一次 rollout（反向的），可能是手工。

**一个半完成的变更被明确记录下来**，比一个框架猜着撤销的变更安全。

## 批次大小为什么从 1 开始

`[]int{1, 10, 100, 0}` 的第一个数字是 1。

第一批的全部价值是「这个变更在真实主机上到底行不行」—— 而 1 台就能回答。如果第一批是 10 台而变更会让 agent 失联，那是 10 台要人工恢复而不是 1 台。

后面的倍数放大是因为一旦 1 台验证过，剩下的风险主要是「不同主机的环境差异」，那个需要样本量才能暴露。

## 和重试的关系

批次里某台失败了，`pulsequeue` 的重试预算仍然适用 —— 失败的 job 会重试。

批次的判定在**重试耗尽之后**：一台重试三次都失败才算这个批次的失败。否则一次网络抖动就会触发熔断，而熔断的代价（整个 rollout 停住，运维来看）比重试高得多。

这意味着 `SettleFor` 要长于重试周期，否则 Gate 看到的是「还在重试中」的中间状态。

## 验收标准

- [x] 批次按序派发，每批等完成（含重试耗尽）再过闸门
- [x] `Gate` 返回 `GateHalt` → 停止后续批次，已完成的不动，有测试
- [x] `MaxFailureRate` 超限 → 停，不调用 Gate，有测试
- [x] 一个永远返回 `GateContinue` 的 Gate 仍然被 `MaxFailureRate` 兜住，有测试
- [x] `SettleFor` 在 Gate 之前生效
- [x] 熔断后的状态可查询：做了哪些、没做哪些、为什么停
- [x] 框架不尝试任何自动撤销
